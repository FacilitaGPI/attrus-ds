Inputs

Form controls — the entry points for user data. Each control captures a single piece of information; together they compose forms, search bars, settings panes, and onboarding flows. Built around a shared .input base with consistent sizing, focus, validation, and inverse rules.

01Intent

Thirteen controls, one anatomy. A field is a labelled question, and the control is only the shape of the answer — so the choice is decided by the shape of the data, not by how the control looks.

Which control

Pick by the answer's cardinality and whether the set is known.

Decision
The answer is…UseNot
Free text, one lineInputTextarea — a one-line answer in a box invites paragraphs
Free text, many linesTextareaInput — the box is the affordance that says "go long"
One of ~2–7 fixed optionsSelectCombobox — search on seven items is friction
One of many, or a searchable setComboboxSelect — a 200-row native list is unusable
One of 2–5, all worth showingRadioSelect — hiding five options behind a click costs a tap and the comparison
A set — zero or moreChipsInput or Checkbox groupSelect multiple — nobody can operate it
On or off, applied immediatelySwitchCheckbox — a switch promises the change already happened
On or off, applied on submitCheckboxSwitch — it lies about when the change lands
A number in a known rangeSliderInput type=number — when the range matters more than the digits
A short code, fixed lengthOtpInput — the cell count tells the user how long the code is
A dateDateTriggerthree Selects — day/month/year is a broken date picker
FilesFileDrop + FileListBoxa bare input type=file — no progress, no removal, no state

03Variants

Twenty variants, organised in five families: text fields (the .input base + affixes), structured fields (group, select, number-input, date), specialised fields (chips, OTP, file, slider), boolean (switch, checkbox, radio), and quiet (underline, pill search). All consume the same focus, error, disabled tokens.

05States matrix

Five canonical states for every text-flavour field: default, :hover (border darkens), :focus (border becomes brand blue + 4px focus ring), filled (value present, neutral border), and validation .is-error. Disabled is universal — opacity 0.5, no interaction. Selection & boolean controls collapse this to off / on / focus / disabled.

06Composition

How fields combine into real forms. The atomic unit is the field — a label, the input itself, an optional helper or error message. Fields stack vertically inside a fieldset; fieldsets stack inside a form. Use grid for multi-column layouts (1 column on mobile, 2–3 on desktop), but never split a single logical field across columns.

Field anatomy

08Don'ts

Patterns that look reasonable in isolation but break the system. Each example pairs the wrong with the right.

Don't · placeholder as label

Placeholder disappears on type. Users forget what the field was for, and screen readers don't always announce it.

Wrong

Do · always label above

Label persists. Placeholder shows format hint.

Right

Don't · red borders without text

Colour alone fails for users with low colour vision. Error must be paired with a message.

Wrong

Do · pair colour with text

Specific, actionable error message. Icon reinforces the state non-redundantly.

Right
Email must include a domain.

Don't · split a field across columns

The label belongs to the input. Splitting them across columns confuses scanning and breaks responsive flow.

Wrong

Do · stack label above input

Vertical pair — scans top-to-bottom, works at any width, accessible to AT.

Right

Don't · disabled looks like filled

If a disabled input is too similar to a filled one, users try to edit it and get frustrated.

Wrong

Do · disabled has reduced opacity

0.5 opacity + not-allowed cursor + --color-background-subtle read clearly as inactive.

Right

Don't · use Switch for forms

Switches imply immediate effect. In a form (where the user must press Save), they mislead the user into thinking the change has applied.

Wrong

Do · use Checkbox for forms

Checkbox state is captured on submit — matches the mental model of "I'll review and confirm".

Right

Don't · radio for boolean

Two radio buttons for yes/no waste space and read as a setting in flux.

Wrong
Email me updates?

Do · single checkbox

One checkbox = one boolean. The label asks the question.

Right

09Accessibility

Inputs are the most-touched control type in any product. They must work flawlessly with keyboard, screen readers, voice control, and touch. The rules below are non-negotiable — every variant in this document already complies.

Requirements

Mapped to WCAG 2.2 AA. Each rule has a concrete implementation.

Touch target≥ 32px on all sides for default size. Boolean controls have a 32px clickable label even when the visual is smaller.2.5.8

10For agents

One sentence settles most of it: a label and its help text are props, never markup you write around the control. Every one of the thirteen ships the same .field anatomy, so hand-rolling it means the label loses its for binding and the error text loses its announcement.

Rules

Each one exists because the alternative silently breaks a11y or state.

Contract
RuleWhy
Pass label, never wrap your own <label>The component generates the id and the htmlFor pair. A hand-rolled label has no binding, so clicking it does not focus the control and a screen reader reads an unlabelled field.
Pass help for error text, not a sibling <div>help is wired to the control for announcement. A sibling div is invisible to assistive tech, so the user hears "invalid" with no reason.
status="error" — never a red border by handStatus drives border, help colour and the aria-invalid flag together. Styling only the border leaves the state unannounced.
Never colour alone for stateError must reach the user as text in help. A red ring is invisible to a colour-blind user and to a screen reader alike.
Use size, never a height overrideThe three sizes are steps of --control-h-*, shared with Button and the topbar. An ad-hoc height breaks alignment in any row that mixes them.
onInverse on dark surfacesIt repoints border, placeholder and help to the inverse ramp. Without it the field keeps light-surface colours and the placeholder falls under 2:1.
A required field says so in the labelThe .req marker is rendered from the label, so required alone gives a browser tooltip and nothing the user can read up front.
Never placeholder as the labelIt vanishes on first keystroke, so the user loses the question exactly when answering it — and it is not announced as a name.

Anti-patterns

Each of these was found in real consuming code.

Avoid
Instead ofDo
A Switch inside a form that submitsCheckbox — the switch says the change already applied, so the user does not press Save
A Select with 40 optionsCombobox — past roughly seven, scanning beats scrolling
Input type="number" for moneyInput with a currency prefix — spinners on an amount are a mis-click waiting to happen

11Behaviour & contract

What the typed layer does for you, and what stays yours. Reading this the wrong way round is how a field ends up with a working border and a broken announcement.

Present the moment you render them.
