Table on mobile

Today the table has one mobile behaviour — every row becomes a label : value card — and that strategy is applied to everything, from a ledger to a selection list. This proposal makes mobile an explicit mode of each variant: a default list row, the existing card stack kept for record review, horizontal scroll kept for comparison data, and a mobile answer for toolbar, filters, sort, selection, grouping, subrows, detail, pagination and empty states.

01Three strategies, chosen per table

A table does not shrink into a phone — it changes shape. The shape depends on what the user does with the data, so the screen picks one with a single prop: mobile="list" | "stack". List is the default; Stack is chosen when the user needs every field of a record visible at once.

List — default recommendedTwo lines per row: who and what on the left, the amount and status on the right. No column labels — the position carries the meaning. For anything the user scans and taps: transactions, payments, counterparties.
Stack — optionEach row becomes a card with label : value lines. Every field visible, nothing to infer. For record review where the user compares fields of one item, not items against each other.

02Toolbar, search and filters

The desktop toolbar puts title, search, filters and actions on one line. On a phone that line becomes three short ones: title with icon actions, a full-width search, and a scrolling chip row for the status tabs. Filters and sort move into bottom sheets reached from icon buttons with a count badge. The four frames are one toolbar in four moments, not alternatives: at rest, the filter sheet open, filters applied, and the sort sheet.

03Rows: states and selection

Row states keep their desktop meaning with marks that survive without columns: selected is a tint, failed is a left rule, returned is muted and struck through. Selection mode swaps the leading avatar for a checkbox and pins the bulk actions to a floating bar, where the thumb is.

04Grouping, subrows and detail

Day dividers stick to the top while their rows scroll under them. A subrow hangs off its parent through a rail, so a fee still reads as belonging to its transfer without a column grid. The detail panel, which opens inline on desktop, becomes a bottom sheet — there is no width to open into.

05Pagination, loading and empty

Numbered pages are hard to hit with a thumb. Mobile keeps the range and two arrows by default (pager="arrows"), or swaps paging for a full-width Load more (pager="load-more"). Loading and empty states are drawn in the list's own shape, so nothing jumps when data arrives.

What this would change in the DS
  • A mobile prop on DataTable (list default, stack for full-record review) and a pager prop (arrows default, load-more) — and the breakpoint unified on the container query at 560px. Today the card stack uses a container query while subrows and the detail panel switch on a 900px viewport media query, so they can disagree inside a drawer.
  • New CSS for the list row (.dt-m-row), the sticky day divider, the subrow rail, the floating selection bar, and the mobile toolbar layout.
  • Detail panel and sort open as a bottom sheet below the breakpoint — a Sheet surface the Drawer can share.
  • Every demo on table.html gains a phone view beside the desktop one, so the mobile behaviour of each variant is visible, not implied.
