Design system

Doc page guidelines

How to author a page in this documentation set. Internal — this is the process behind the system, not a part of it. Nothing here ships to a consuming product.

01Why this exists

A design system is consumed twice: by a person reading a page, and by an agent reading a contract. The second reader is new, and it changes what a doc page owes. An agent cannot infer that danger is wrong for emphasis, or that two callouts in a row defeat both — it needs those stated.

An audit of the 50 pages found the full pattern on 6, partial on 8, and minimal on 36 — and the complete ones were the most recently written. The heaviest-used components (Button, Input, Table, Tabs, Toast) were the least documented, so the agentic contract covered exactly what an agent reaches for least.

Two working rules come out of that. State the negative: a page that lists only what a component does leaves every misuse available. Separate shipped behaviour from your job: copying markup does not buy keyboard nav or ARIA, and a page that does not say so invites a broken copy.

02Three profiles

One mould does not fit. A spacing page has no props and no anti-patterns; forcing the component structure onto it produces empty sections, and empty sections teach people to skim.

Profile A

Component

Anything a consumer instantiates: Button, Input, Table, Drawer, Callout. Carries props, states and behaviour, so it carries the full contract.

10 sections · #ds-api required
Profile B

Token / foundation

A scale rather than a thing: colour, spacing, radii, shadows, typography, motion. The decision is which step, not which props.

5 sections · reduced #ds-api
Profile C

Guide

Prose with a point of view: theming, composition, naming, this page. Structure follows the argument; only the chrome is fixed.

Free structure · chrome required

Pick the profile before writing. Most mistakes in the current set are a component page missing sections, or a token page padded with sections it never needed.

03Chrome — all three profiles

Fixed order, top to bottom. Every item earns its place: the card registers the page, the controls make dark mode verifiable, the contract makes the page machine-readable.

#ElementWhy it is required
1@dsCard commentFirst line of the file. Registers the page in the catalog and supplies its thumbnail — without it the page exists but nobody finds it.
2.doc-backReturn to the index. The only element already on all 50 pages.
3.view-controlsTheme toggle, plus the product selector on pages where matiz matters. A page without it cannot demonstrate its own dark mode — today 36 pages cannot.
4.doc-headerh1, a one-sentence lead, and a .doc-meta-pill carrying status: Stable, Beta, Deprecated or Internal.
5.api panelProfiles A and B. Import, CSS class, variants, key props, and a Prefer line. The panel is the human contract.
6#ds-api JSONThe machine contract — same facts, no prose to interpret. See §06.
7.doc-navNumbered anchors. Numbers must match the section badges — drift here caused three separate bugs in this set.
8SectionsPer profile, §04 and §05.
9.doc-footPage name, data-ds-version hook, link back. Never a hardcoded version or date.

Where the file goes. Doc pages live flat in preview/, named after the component in kebab-case (preview/toggle-chip.html). Canonical CSS goes in preview/components/. Do not scaffold from scratch — copy the closest page in the same profile and replace its content, so the chrome stays identical by construction rather than by discipline.

Load every components/*.css with a cache-buster (?v=N). Un-versioned sheets cost three separate debugging rounds in this project — measurements were taken against CSS that no longer existed on disk.

04Profile A — component page

Ten sections. The order moves from decision to detail: an agent that stops reading after §01 should already know whether this is the right component.

#SectionReqContents
01IntentyesOne sentence of what it is. Use when — three conditions that must all hold. Use instead — routes to other components when they do not.
02AnatomyyesStructure tree plus one demo with each part labelled. Name every slot the consumer can fill.
03VariantsyesOne row per variant: what it changes and when to reach for it. Not a gallery — a decision table.
04SizescondOnly if there is a scale. Show the --control-h-* token, not a literal — a page that prints 40px while the token says otherwise is the drift we keep fixing.
05Statesyeshover · active · focus-visible · disabled · loading · error — whichever exist. Disabled and focus are the two most often skipped and most often wrong.
06CompositioncondHow it sits with other components, and which pairings are wrong. Include the case that looks fine and breaks — a bar inside a card, a spacer beside a stepper.
07On inverseyesDark surface treatment. State the measured contrast, not "looks fine" — most contrast bugs in this system were invisible until measured.
08For agentsyesAnti-patterns (what fails and why it survives review) and Rules (deterministic constraints an agent can apply without judgement).
09BehaviouryesThree blocks: ships in TSX · CSS-only must implement · presentational only. This is what stops a copied footer from becoming a promise nobody keeps.
10Class mapyesEvery class in the CSS with its role. If a class exists and is not here, one of the two is wrong.

Writing the anti-patterns

This is the section that makes a page agentic, and the easiest to write badly. Each row needs the failure and the mechanism — "don't stack callouts" is a rule to memorise; "stacked, they become a list with decorative boxes and the reader skips all of them" is a reason that generalises.

Prefer anti-patterns that render without error. Those are the ones that survive review and reach production. A misuse that throws is already caught by the compiler.

05Profile B — token page

Five sections. The reader's question is not "how do I call this" but "which step do I pick, and why not the one next to it".

#SectionContents
01ScaleEvery step: token, value, intended use. Include the measured rendering when it can differ from the declaration — the weight scale advertised seven steps and drew four.
02SemanticsWhich token for which intention, and the raw-versus-semantic rule: raw scales are for authoring tokens, semantic tokens are for components.
03In contextThe tokens applied to real UI. A wall of swatches shows the palette; it does not show that two adjacent steps are indistinguishable at 1×.
04For agentsAnti-patterns (raw where a semantic exists; off-scale values; a token the typeface does not contain) and how to choose between neighbouring steps.
05ReferenceThe complete table, copyable, matching the export.

06The #ds-api contract

A JSON block near the top of the page. It repeats what the prose says, with nothing left to interpretation — an agent should never have to parse a paragraph to learn that rounded requires bar.

<script type="application/json" id="ds-api">
{
  "component": "Callout",
  "import": "const { Callout } = ATTRUS",
  "cssClass": ".callout",
  "status": "stable",
  "intent": // one sentence
  "variants": [],
  "props": [{ "name", "type", "default", "note" }],
  "useWhen": [],        // conditions that must all hold
  "useInstead": [{ "when", "use" }],
  "antiPatterns": [],
  "constraints": [],    // deterministic, no judgement needed
  "behaviour": {
    "shippedInTsx": [],
    "cssOnlyMustImplement": [],
    "presentationalOnly": []
  }
}
</script>

Profile B swaps props and behaviour for tokens[] and chooseBy[]. Profile C needs no contract.

The panel and the JSON are generated by tools/gen-api.cjs from the .d.ts plus tools/api-meta.json. Hand-editing either one works until the next regeneration overwrites it — put non-derivable fields (intent, antiPatterns, constraints) in api-meta.json and run the generator.

07The doc kit

Documentation components, so a page composes instead of reinventing. Today each page declares its own table class — .cls, .tk, .map, .g — which is why they drift.

Demonstration

ComponentUse
.demo-card + -head -canvas -noteThe canonical frame for any demo. Head states what is shown; note carries the caveat.
.is-plainComponent already has its own card — no second surface.
.is-inverseDemonstrating an .on-inverse variant.
.is-checkeredRequired for translucent components. Glass over flat paint is indistinguishable from opaque — the stage has to carry the pattern the blur samples.
.is-scrollingSticky or frosted chrome. Gives the blur something to move against; a static frosted bar demonstrates nothing.
.is-gridSpacing and layout demos.
.demo-itemWhen one stage shows several states, each gets a mono caption. The reader should not count positions.

Contract and tables

ComponentUse

.api-preferThe Prefer line — the single most useful sentence on the page for an agent.

.doc-table.is-tokensToken · value · use.
.doc-table.is-contractBehaviour · how it is built. The "how" is what stops re-implementation.

Guidance

ComponentUse
.calloutCaveats inside the doc. Use the real component — the docs should eat their own cooking.
.do-dontSide-by-side visual pair. Stronger than prose when the failure is spatial.
.rule-listNumbered deterministic constraints.

08Surfaces — nothing floats

Every block on a doc page sits on a surface. A page where the demos have cards and the prose does not reads as unfinished, because the eye takes the bare text for a gap between things rather than a thing itself.

The SmartSearch page shipped with six carded demos and eleven bare tables — then over-corrected, putting a card around the page title too, which stole the entry point from the first demo. Nothing was broken and every value was right — it simply looked like a draft next to buttons.html. Surface is not decoration; it is what tells the reader where one block ends.

The rule

Content sits on a card. Titles do not. Anything that renders substance — a demo, a table, the API panel — carries a surface, because the surface is what marks where the block begins and ends. The page title with its description, and each section title with its lead, stay bare on the canvas.

ElementSurfaceReasoning
Page h1 + descriptionBareThe title is the way in. Boxing it makes it compete with the first demo for that role, and the reader loses the top of the page.
Section h2 + .leadBareA lead introduces the blocks under it. Give it a card and the section reads as four blocks where the first one is prose — the hierarchy flattens.
Demo, table, API panelCardThese are the blocks. Without a surface the reader takes bare content for the gap between things rather than a thing itself.

The asymmetry is the point: bare type reads as structure, carded content reads as substance. A page that boxes everything has no hierarchy left, and a page that boxes nothing looks unfinished.

The four surfaces

BlockClassCarries
Page title.doc-headerNo surface. The title and its lead sit bare on the canvas — a card around them competes with the first demo for the reader's entry point.
API contract.apiSame surface, tighter padding. It is a reference panel, not a demo.
A demo.demo-cardHead + canvas + optional note. The canvas picks its own stage — see §07.
A table.token-tableSurface with overflow: hidden so the radius clips the first and last rows.
Section lead.leadNo surface. A section's title and lead are also bare — they introduce the blocks below rather than being one.
Body prose.bodyBare as well. Prose earns a surface only inside a card, where the card supplies it.

One surface, never two

A table inside a .demo-card-canvas must drop its own surface — the card already supplies one, and nesting them produces a frame inside a frame with a double hairline down the middle. The rule is a one-line override on the page:

/* The card owns the surface; the table inside it does not */
.demo-card-canvas .token-table {
  background: transparent;
  border: 0;
  border-radius: 0;
  box-shadow: none;
}

The same applies to a callout inside a card, or a code block inside a demo canvas. Ask which element owns the box, and strip the surface from everything inside it.

A page must declare what it uses

The chrome classes are not global. .doc-header, .api, .token-table, .page-theme and .lead are declared in each page's own <style> block — only demo-card.css and the component sheets come from styles.css. A page that uses a class it never declared renders as the browser default and looks like a draft: the SmartSearch toggle rendered as a native button, and its tables sat with no surface, because both classes existed in the markup and nowhere in the CSS.

This is why §03 says to copy the nearest page of the same profile rather than scaffold. The chrome arrives complete, and the classes you write are already declared.

Stylesheet order

Four links, in this order, and the reason is cascade: tokens must exist before anything reads them, the theme file overrides token values, and the component sheets read the result. The page's own <style> comes last so it can adjust without !important.

1 ../colors_and_type.css        tokens
2 ../themes/index.css?v=1       product overrides
3 components/<name>.css?v=N     the component under test
4 <style> … </style>            page chrome

Every components/*.css link carries ?v=N. Without it the browser serves a cached sheet and every measurement you take is against CSS that no longer exists on disk — this cost three rounds of debugging on the table subrow reveal, where an inline 38px lost to a max-height: 0 that had already been deleted.

Table naming — pick one

This set accumulated four names for the same table: .cls, .tk, .map and .g. Each was declared locally in one page, and two of them declared no surface at all — which is exactly how a page ends up with loose content while looking correct in the source. .token-table is the name, matching buttons.html, the largest page in the set.

Table useColumns
Class mapClass → what it owns. Not "description" — owning is what distinguishes a real map from a restatement of the name.
Anti-patternsAnti-pattern → why it fails. The second column must name the failure, not repeat the rule.
Behaviour contractBehaviour → how it is built. The reader needs the mechanism to know whether their own version matches.
TokensConcern → tokens. Grouped by concern, so a change has one row to check.
PrecedenceSituation → component. Short enough to scan in a tie-break.

Card or table?

ContentUseBecause
Rendered component, any state.demo-cardIt needs a stage, and the stage has to be chosen — checkered for translucency, inverse for dark variants, scrolling for sticky chrome.
Rows of the same shape.token-tableThe reader scans a column. A card per row would hide the comparison the table exists to make.
A rule with a rendered exampleCard containing a tableCard supplies the surface and the label; the table carries the rows. Strip the table's surface.
One paragraph of reasoningBare .bodyProse is connective tissue, not a block. Rhythm (§09) keeps it from touching what follows.
Titles and leads are the exception, and the only one: they are bare by design. Everything else that renders content — demos, tables, the API panel — carries a surface. Walking a section's children, anything with content and no background that is not a heading or a lead is floating.

09Vertical rhythm & visual refinement

The most common defect in this set is not a wrong colour — it is two blocks touching. A component correctly ships no outer margin, so if the page does not own the space between blocks, nothing does.

This page had the bug while describing it. The callout in §01 sat flush against the paragraph below it — measured gap 0px — because .callout declares no margin and no page rule supplied one. That is the whole failure mode in one line.

Why components ship no outer margin

A component cannot know what sits above or below it, so any margin it carries is wrong somewhere: doubled next to a sibling that also has one, unwanted as the last child of a card, fighting a grid gap. The rule is the container owns the space between its children. The consequence for a doc page is that it must declare that space explicitly — a page that only styles its own components will have blocks colliding.

The rhythm scale

Four steps, and the relationship between them is what reads as structure: the gap between sections must be clearly larger than the gap inside one, or the reader cannot tell where a section ends.

BetweenTokenReasoning
Two sections--space-10The largest gap on the page. It has to beat every internal gap or the sections merge.
Section lead → first block--space-6Enough to separate the prose from the evidence.
Two blocks in a section--space-6Same as above — sibling blocks are peers.
Sub-heading → its block--space-3Tight, because the heading belongs to what follows. Its top margin is large (--space-8): a heading is far from what it leaves and close to what it introduces.
A callout answering the paragraph abovenegative --space-2Deliberate. When a callout qualifies the sentence before it, the default gap makes it look like a new topic — pulling it up binds them.

Where blocks collide

SymptomCauseFix
Two blocks flush against each otherNeither declares a margin on the facing edge — typical when one is a component and the other a bare <p>.Give the section a rule for its block children, not the component a margin.
Extra space at the bottom of a card or sectionThe last child still carries its margin.> *:last-child { margin-bottom: 0 } on the container.
Doubled gap between two paragraphsOne carries margin-bottom, the next margin-top, and they do not collapse across a flex or grid parent.Pick one direction and use it everywhere. This set uses margin-bottom only.
A heading closer to the text above than belowSymmetric margins on the heading.Asymmetric: large top, small bottom. Proximity is what assigns the heading to a block.
Uneven gaps in a row of demosMargins on the items instead of gap on the parent.Use gap. It survives an item being removed or reordered; margins do not.

Refinements worth a second pass

CheckWhat to look for
Optical alignmentTwo type sizes on one row centre their boxes, not their letters — the smaller one floats up. The live indicator in the topbar needed line-height: 1 on both children before the clock sat on the label's baseline. Any row mixing sizes deserves this look.
Hairline weightA border inside a tinted box competes with the tint. The Callout default went from 22% to 12% ink because the outline was drawing a rule around a note meant to recede.
Emphasis hierarchyInside one block, the order should be surface → border → text. If the border is the loudest thing, the block reads as a control rather than a note.
Nested emphasisA button inside a callout must be quieter than the callout, which is quieter than the page. Its fill went 14% → 10% for exactly this reason.
Line lengthCap body copy near 74ch. A lead spanning the full 1060px is measurably harder to track back to the next line.
TruncationAny single-line label in a flexible container needs min-width: 0 on the flex item plus text-overflow on the text. Missing either one lets labels overlap instead of truncating.

How to check it

Read the gaps, do not eyeball them. Walk a section's children and measure the real distance between consecutive boxes: next.getBoundingClientRect().top − prev.getBoundingClientRect().bottom. A 0 is a collision, and a value that does not appear in the rhythm scale is an accident. This is how the callout on this very page was found.

10What every demo must cover

A page can hold ten cards and still miss the states that break in production. These four are the ones this project shipped bugs in, each because a demo did not exist to reveal them.

DimensionWhy it needs its own demo
Both themesNot a screenshot in one and a claim about the other. Tokens that resolve to a fixed light value read at 1.05:1 on ink — --color-brand-text did exactly that across eight consumers, and only measurement in dark found it.
Narrow widthShow the component at its collapse point, and use the modifier (.is-compact) rather than trusting the viewport: a media query cannot see that the component sits in a split pane or a drawer, so the desktop layout survives into a container with no room for it.
Reduced motionAnything that animates needs prefers-reduced-motion in the CSS and a line saying so. A reveal built on a height transition becomes a jump — which is correct, and should be stated rather than discovered.
Overflowing contentLong labels, two-line wraps, big numbers. Stepper labels overlapped into "AtivaçãoRecebimento" because every demo used short words; the fix was truncation, but the miss was the demo.
Text direction is not covered by this system yet. If RTL becomes a requirement, it joins this table — and every margin-left, padding-left and ::before connector in the component CSS becomes a logical-property migration.

11Lifecycle — the page is not the only artefact

A component lives in five places. Touching one and not the others is how this set accumulated drift: the weight migration updated CSS, TSX and the app, and left the typography page advertising a scale that no longer existed.

ArtefactWhereRole
Canonical CSSpreview/components/<name>.cssThe visual source of truth. Everything else follows it.
Typed componentcomponents/<Name>/<Name>.tsx + .d.tsProps, behaviour, ARIA. The .d.ts feeds the generated API panel.
Benchcomponents/<Name>/<Name>.htmlProves the props are wired. A CSS class can be styled correctly while the prop never reaches it.
Doc pagepreview/<name>.htmlThe spec a person consults and an agent parses.
Catalog cardpreview/index.html + @dsCardWithout it the page exists and nobody finds it.

Adding a prop touches five files

The .d.ts, the CSS, the bench, the doc spec, and the generated contract. Skipping the bench is the expensive one: verifying with classList.add in the console proves the CSS works, not that the prop is connected — a prop that falls through to ...rest leaks as a lowercase DOM attribute and looks fine in a screenshot.

Adding a token touches five files too

colors_and_type.css, both export JSONs, the export README, and the two count surfaces on the homepage. Verify the count by measuring the :root block, never by incrementing the number you remember.

Deprecating

Keep the old name resolving to the new one, mark it in the CSS comment, and say so on the page — the three phantom weight tokens survive as aliases so consuming projects do not break, while new code is told to use the four real ones. Then record it in the changelog with the measurement that justified the change, so the next author does not re-run the same test.

12Writing rules

The prose carries as much of the contract as the tables. These are the habits that made the difference across this set.

RuleBecause
State the mechanism, not just the verdict"Don't use danger for emphasis" is memorised. "Danger is the only tone that sets role="alert", so spending it means the next real error announces nothing new" generalises to cases the page never listed.
Give measured numbers"Good contrast" is unfalsifiable. "4.26:1 on the tinted fill" can be checked, and caught when it regresses.
Name the failure that rendersA misuse that throws is caught by tooling. Document the ones that look correct.
Never hardcode a number that lives in a tokenPage and token drift, the page loses, and it is copied anyway. Use the hook or name the token.
Say who implements whatEvery page describing keyboard behaviour must say whether it ships or is the consumer's job. Otherwise a copied footer becomes an unkept promise.
One idea per demo cardA card showing four things teaches none. Split it, and let the head sentence say which one this is.

13Before you publish

Fourteen checks. The first four are mechanical and have each broken a page in this set.

#Check
1Nav numbers match section badges, and every anchor resolves.
2One <main>, opened and closed; no section outside it.
3Every components/*.css link carries ?v=N.
4No hardcoded version, date or token count — use the hooks.
5Theme toggle present, and the page verified in both themes.
6Every class in the component CSS appears in the class map.
7#ds-api parses, and its facts match the panel.
8Anti-patterns and constraints filled — not a placeholder.
9Every aria-label is a human phrase, never a CSS class name. Generated demos inherit this mistake in bulk.
10Demos cover both themes, the narrow width, reduced motion and overflowing content (§10).
11The other four artefacts are in sync — CSS, TSX, bench, catalog card (§11).
12Demos, tables and the API panel sit on a surface; titles and leads stay bare; no surface nests inside another (§08).
13No two blocks touch — every gap in a section matches the rhythm scale (§09).
14Anything measured on the page was measured after the last change, not inferred from an earlier run.
Enforce, don't remember. Checks 1, 3, 6 and 7 are mechanical enough for tools/drift-linter.html to own: fail when a component page has no #ds-api, when a CSS class is missing from its class map, or when a stylesheet link is unversioned. Without that, the next page is written outside the pattern and the audit repeats.
